# CodeHealth · 本地代码体检中心

一个在本机运行的中文 Java / Maven 代码质量平台。支持项目登记、本地规则检查、SonarQube 完整体检、问题定位、真实历史趋势、基线比较、报告导出、质量门禁与环境检查。

## 新增的日常开发功能

- **连续审查与详情保护（v1.20）**：保存审查后回到原修复或 PR 清单页，支持取消返回；关闭报告或切换窗口后，旧的详情响应不再弹出或覆盖编辑。新增延迟响应和重试验证，审查不会解除自动门禁。
- **报告与修复清单轻量显示（v1.19）**：扫描详情只读取所需显示证据，修复和 PR 清单每页最多 25 条。排序、审查、验收和完整导出保留；新增 62 个问题的真实翻页、审查、下载验收。
- **简洁界面与按需配置（v1.18）**：导航按检查验收、任务知识、设置整理分组；“AI 质量控制”改为功能更明确的“代码审查与证据”。去掉无操作作用的用户装饰，窄屏可展开文字菜单。设置页先说明零额外配置的本地检查，完整体检和可选服务管理按需展开，原有功能均保留。
- **页面数据及时释放（v1.18）**：关闭详情清除隐藏正文和编辑快照，离开列表中止读取并释放缓存；扫描轮询不并行叠加，隐藏页面暂停页面读取。现有服务仍按需读取完整报告。独立小型样本空闲约 45–46 MB，30 次扫描完成后约 73 MB；这是当前实测服务占用，不是全场景上限或优化降幅。见 [简洁使用与轻量运行指南](docs/SIMPLE-WORKFLOW.md)。
- **新增页面验收（v1.18）**：固定页面回归扩展至十类，增加可选配置的成功/失败保存与关闭详情/离开列表释放数据，并实际检查窄屏文字导航。

- **需求与任务管理（v1.17）**：填写需求、验收条件和允许改动范围，关联任务并跟踪领取、处理、提交、人工审核、退回与阻塞。需求改动使旧任务证据失效；扫描问题可直接转为跟踪任务，要求实际扫描验收的任务会再次核对最新报告与当前代码。
- **问题知识库（v1.17）**：保存问题表现、原因、处理方法、真实验证与标签，从已审核任务沉淀经验。草稿经人工审核才发布；已发布知识可撤回再编辑，任务上下文推荐相关已发布经验，历史随备份保留。
- **本地 agent 参与（v1.17）**：授权指定项目，通过本机接口或随附命令行工具查询任务、读取上下文、领取/续期/释放、提交证据与提议知识。有效领取防止重复处理，凭据撤销或重启后失效；agent 不能自行批准成果或发布知识。这是可信本机协作，不是恶意进程隔离。见 [本地 agent 与协作使用指南](docs/LOCAL-AGENTS.md)。

- **一键迭代验收（v1.16）**：在“验收流水线”点击“查看本轮验收”，连续执行平台自检和八项页面回归，保存组合报告与截图。只有两类完整证据对应同一版代码才通过，失败或中断不能沿用旧成功。也可运行 `npm run check:iteration`，详见 [自动验收使用说明](docs/AUTOMATED-ACCEPTANCE.md)。
- **GitHub 自动验收（v1.16）**：提交 main、打开拉取请求或手动触发时，按锁文件安装依赖，实际执行相同的一键验收；报告与失败截图保存 14 天。使用 Windows / Node 24 / Chromium，自动检查结果不代替业务全覆盖或真实 Java 构建。


- **业务场景自动验收（v1.15）**：编辑验收方案时，可将场景绑定到 `测试类#测试名称`。完整体检会从本次 Maven 构建的新报告中精确匹配结果；失败阻断，缺失或跳过保持未验证。自动结果不能手工改成通过。未绑定场景仍按真实人工执行记录。
- **真实页面自动回归（v1.15）**：在“验收流水线”点击“查看页面回归”，自动使用独立示例数据执行八项真实浏览器流程，保存逐项结果和截图；最新结果与当前代码核对，改动后要求重跑。结果和截图随备份恢复。安装依赖后可运行 `npm run check:browser`。见 [自动验收使用说明](docs/AUTOMATED-ACCEPTANCE.md)。


- **平台自身检查（v1.14）**：在“验收流水线”点击“检查平台自身”，实际检查本平台的 JavaScript 语法并执行全部 Node 自动测试。失败、取消、跳过、待办、缺少完整汇总或执行期间代码变化均不能通过。结果可下载并随数据备份保存；再次打开会核对当前代码，改动后要求重跑。也可运行 `npm run check:platform`，独立报告保存在 `outputs/platform-check`。结果只覆盖自动自检范围，不替代业务、视觉或真实 Java 构建验收。
- **验收误判修正（v1.14）**：源文件版本核对加入 JavaScript/TypeScript、HTML/CSS、Vue/Svelte，排除 outputs/dist/coverage。旧版较窄的指纹需要重新扫描；历史报告保留。没有任何 Java/SQL 文件的本地扫描不再因为“零问题”显示通过。
- **验收流水线（v1.13）**：侧栏新增八阶段验收，提供八类、30 个可编辑场景，逐项定义输入、步骤和预期。自动阶段接入已有本地检查、构建测试与质量门禁；业务场景实际执行后记录通过、失败或有理由不适用。失败、未验证、旧代码证据和旧方案不能通过验收。保存方案生成新版本，新扫描不继承场景通过；支持复验历史、详细导出和备份恢复。完整要求默认启用，缺依赖不会伪装成功；本地方案明确不包含自动构建测试。见 [详细验收指南](docs/ACCEPTANCE-PIPELINE.md)。
- **当前验收判断（v1.12）**：总览和项目管理点击“现在可以验收吗？”，按项目最新一次尝试显示完成情况、自动门禁、当前代码核对、自动测试记录、人工证据及下一步操作。失败、运行中或更新后的尝试不会被旧成功记录代替。验收表也按需核对当前文件；页面结果只对应核对时刻，保存验收仍会再次核对。局部检查明确显示范围，本地通过不证明编译或测试通过。历史验收记录保留原样；只读核对不会改写原报告。PR 状态仅对应固定提交，不核对远程最新状态。
- **问题审查与跟踪（v1.12）**：问题中心、修复任务和 PR 详情可记录待审查、已确认、修复中、已排除，所有保存需 8–2000 字理由。问题中心支持按审查状态筛选，导出保留相同筛选与审查理由。相同项目 / PR、范围、方式、规则配置与实现版本的最新完成报告传递审查记录；编辑更旧的报告仅改变该报告。证据相同的普通问题可跨行号变化保持判断；证据变化或消失后再次出现会重新打开，并保留之前理由。含脱敏证据的本地问题需整个文件指纹一致；无指纹的脱敏 PR 问题不会继承排除。相同证据的重复问题在文件变化时保守重新审查。改名视为新问题；启发式匹配不能证明修复语义。已排除不隐藏问题，不修改自动门禁或解除高风险阻断。
- **审查记录保存**：记录随完整报告、归档和备份保存，不加入常驻摘要。每条最多保留 50 次人工判断，每份传递记录最多 10,000 条，保存时审查证据最多 2 MB；达到上限明确拒绝新保存并保留原记录。新扫描携带已消失问题的历史判断，以识别再次出现，不自动清空旧理由。检查或其他审查保存期间暂不能保存问题判断，避免写入覆盖。
- **异常文本与规则性能（v1.11）**：注释 / 字符串处理、空 catch 和凭据赋值识别避免反复回溯长文本。长串未闭合的块注释、Java 字符串或 SQL 引号会明确指出文件并记录“检查未完成”，不能验收或设为基线。空 catch 支持含参数括号的注解及多异常类型；注释和字符串中的示例仍被排除。规则实现版本升级后，旧基线仍保留，但需要新版扫描重新设置才能进行兼容比较。规则仍是启发式提示，不是完整 Java/SQL 语法解析器或编译器，其他语法错误不保证被发现。
- **代码版本核对（v1.10）**：新本地扫描记录源码与常见配置的 SHA-256 指纹，扫描前后核对；过程中发生变化会记录为检查失败 / 未完成。“扫描详情”和“人工验收”可点击“核对当前代码”，列出新增、修改和删除数量及最多 25 个路径。保存验收时自动核对；文件变化、不可读或旧报告无指纹时保留人工证据，但验收受阻。Git 改动报告还核对 HEAD 基准。门禁保留当时自动结果，版本核对不代替业务、构建或测试验证。
- **版本核对的范围与资源（v1.10）**：包含 Java/Kotlin/SQL、XML、properties、YAML、JSON、Gradle/Kotlin 构建和 sh/ps1/cmd/bat 脚本；排除 `.git`、`.idea`、`.codegraph`、`target`、`node_modules`、`data`、`build`，不跟随符号链接。不覆盖其他扩展名、外部依赖、运行环境或数据库变化。最多 50,000 文件、200,000 目录项、单文件 5 MB、总计 512 MB、核对 120 秒。顺序读取 64 KB 块，不保留源文，文件清单仅存在完整报告，常驻索引不保存。按需核对只证明当时纳入范围的内容，后续变更需重新核对；没有持续文件监控。JSON/Markdown 导出及备份保留版本证据，历史报告不会补写指纹。
- **可恢复归档（v1.9）**：项目管理可归档停用项目；扫描历史和 AI 质量控制可单份或批量归档旧报告。归档中心按页查看、筛选与恢复。最新检查、最新已完成全项目结果、基线及每个 GitHub PR 的最新检查不能归档，避免整理时隐藏当前风险。归档不删除源码或报告，原验收证据与要求保留。项目归档会从当前问题统计中移出，恢复后重新纳入；项目历史仍可查看。报告恢复保持原检查时间顺序。
- **历史摘要按需读取（v1.9）**：归档报告的摘要移到磁盘，常驻索引只留编号；页面每次读取一份摘要、最多保留两页匹配项。完整报告仍按需读取。备份包含归档索引、摘要和原报告；归档或备份期间暂停并发写入。该优化减少常驻历史数据，不是进程总内存上限，也不会释放磁盘空间。
- **项目质量约定（v1.8）**：在项目管理的“质量约定”或质量门禁中，按项目要求完整 AI 任务约定、完整体检、最低执行测试数、中风险为零，以及项目自己的新代码覆盖率 / 重复率阈值。“填写严格建议”只填表，保存后才生效。全局扫描规则仍对所有项目生效；项目阈值只在完整体检中使用。GitHub PR 不自动关联本机项目约定。
- **构建测试数量（v1.8）**：完整体检成功执行 clean 构建后，只统计这次构建开始后更新的 Maven Surefire / Failsafe `TEST-*.xml`。执行数为测试数减去跳过数；任何报告不支持、统计异常、过大或读取中变化都会使数量不可核实。未运行完整构建、没有新报告或没有达到要求时，不会满足最低数量约定。报告统计不能证明业务场景已覆盖，人工验收仍需核对真实行为。当前环境仍未执行真实 JDK/Maven/Sonar 全流程；报告解析与门禁逻辑通过代表性数据和本地流程验证。
- **高风险与历史要求（v1.8）**：完整体检的 Sonar 通过结果不能覆盖已发现的 HIGH / CRITICAL / BLOCKER 风险。项目约定与有效阈值随扫描保存，后来修改不改变旧报告；要求或阈值不同的扫描不作基线比较。扫描详情和修复清单导出保留未满足要求与测试统计。
- **备份与迁移（v1.7）**：环境设置中点击“创建数据备份”，下载压缩备份。包含项目、历史报告、基线、任务约定、验收证据及已导出的清单，不包含当前进程的 Token、项目源码、旧备份和 SonarQube 数据库。只能在检查和保存完成后创建；创建期间暂停新的写操作，读取页面仍可使用。
- **数据目录保护（v1.7）**：同一数据目录只允许一个平台进程使用，即使端口不同也不会同时写入。正常关闭时清理锁；强制结束或断电可能留下锁。只有确认原进程已经结束，恢复工具才允许清理旧锁，不会结束其他进程。
- **大项目检查与停止（v1.6）**：规则检查使用临时独立线程，检查期间页面和服务仍可响应；扫描详情显示已检查的源文件数，可停止正在执行的本地规则阶段。停止会记录为检查失败 / 未完成，不能验收或设为基线；Maven 与 Sonar 阶段不提供此停止按钮。线程结束后释放，不常驻。
- **检查资源上限（v1.6）**：最多 50,000 个源文件、单文件 5 MB、10,000 条启用规则问题；证据最多 500 字并先脱敏。文件超限、问题超限、线程内存超限或超过 10 分钟时明确失败，不输出部分检查“通过”。线程的 V8 老生代上限 96 MB、年轻代上限 16 MB，不等于整个进程的 RSS 上限。运行状态的进程内存包含检查线程，堆读数仅为主服务。完整检查仍会使用额外的 JDK / Maven / Sonar 内存。
- **旧基线兼容性（v1.6）**：本轮调整了证据的长度与格式，旧规则版本的报告不会被用于判断新版问题“消失”；请用新版重新扫描后设置基线。旧报告、验收和导出仍可查看。
- **AI 任务约定（v1.5）**：在“AI 质量控制”中按项目填写目标、允许改动范围、约束、验收场景、测试计划和恢复方案。可保存草稿，完整填写后预览并导出 Markdown 给 AI 使用。完整状态只表示约定已填写，不表示代码通过。新扫描保存当时的约定全文与版本；编辑项目约定不改变旧报告。约定正文按需读取，首页只保留小摘要。GitHub PR 不自动关联本机项目约定。
- **验收缺口（v1.5）**：打开“验收”，直接查看自动检查阻断、缺失的五类人工证据、检查范围和未执行的编译 / 测试 / 覆盖率，以及本次扫描绑定的任务约定。修复清单导出也保留这些内容。填写证据不会自动执行测试或判断代码是否符合文字需求；后续代码改动仍需要重新检查。
- **本次 Git 改动体检**：扫描选择“本次 Git 改动”，对照当前 HEAD 检查暂存、未暂存和未跟踪的 Java / SQL 文件。只显示改动行附近的问题；过长 Service、重复迁移版本按受影响文件判断，并保留项目上下文。未初始化 Git 的项目会给出清楚提示。已提交的改动不在这个范围内。
- **扫描前检查**：点击“检查准备情况”，查看目录、Maven 项目、Git、JDK 版本、Maven / Wrapper、Token 与 SonarQube 服务是否就绪。点“开始检查”也会先验证，缺少依赖时保留提示供你处理，不会继续构建。已运行的 SonarQube 无需再要求本机 Docker 启动。
- **修复任务清单**：在问题中心或扫描详情打开任务列表。任务按风险排序，包含位置、规则、修复建议和验收要求，可导出 Markdown 到 `data/reports`，交给 Codex 使用。不会调用外部 AI 或自动改写业务代码。
- **进度和对比**：扫描详情自动更新阶段与耗时，完整体检分别显示准备、规则、构建、提交分析、等待处理和读取结果。整体扫描可与基线或上次同类检查比较新增、消失、仍存在的问题及实测指标变化。规则、范围不同的扫描不能被当作可直接比较的结果。

本次改动检查不会覆盖总览与问题中心中的整体项目结果，也不能设为整体基线。没有待检查的 Java / SQL 文件时门禁显示“待评估”，不会以没有扫描到代码为由宣布项目通过。本地比较按规则 / 文件 / 证据及出现次数匹配，单纯移动行号不会当作修复；修改证据内容仍可能被记录为一条消失、一条新增，需结合代码确认。

建议的 AI 开发流程：先保存任务约定并导出给 AI → 实现后检查本次 Git 改动 → 查看风险并修复 → 实际运行测试、验证验收场景 → 重新扫描并记录证据。每个项目保留当前约定，之前的扫描保留自己的版本。约定保存在本机 `data/briefs`；备份和迁移时应复制整个数据目录，不能只复制 `state.json`。不要在约定中填写凭据或敏感信息。

想采用较严格的控制，可先在项目质量约定点击“填写严格建议”：要求任务约定、完整体检、至少 1 个执行测试、中风险为零、新代码覆盖率 80% 和重复率不超过 3%。根据项目实际成熟度调整再保存。本地规则依然可以运行，用于发现风险；严格要求下缺少完整数据会阻断验收，不妨碍你继续修复代码。

### 使用压缩备份迁移

解压平台迁移包并准备 Node.js 20+。在平台目录打开终端，将下载的备份恢复到**不存在的新目录**：

```powershell
node scripts/restore-backup.js "D:\Downloads\backup-编号.jsonl.gz" "D:\CodeHealthData"
.\scripts\start.ps1 -DataDirectory "D:\CodeHealthData"
```

恢复前验证 SHA-256 校验、文件路径、索引、报告、基线和任务约定引用；不会覆盖已有目录。恢复发布期间也持有目录锁。失败会保留带 `.restoring-编号` 后缀的暂存目录供检查，原数据不受影响。备份每个文件最多 32 MB，总解压数据最多 2 GB；达到上限会明确失败。没有新增 npm、Python 或 Docker 依赖。备份格式为平台专用的 gzip 压缩记录，使用上述恢复工具读取。

迁移后在项目管理更新源码目录，在环境设置更新 JDK 路径并重新填写 Token。SonarQube 数据库与 Docker 卷需要单独迁移。

如果异常退出后启动提示数据目录被占用，在平台目录执行：

```powershell
node scripts/recover-lock.js "D:\CodeHealthData"
```

工具拒绝清理仍在运行或信息不完整的锁。PID 被其他进程复用时也会保守拒绝。正常关闭会等待正在进行的保存、备份与完整构建结束；强制关闭后用恢复工具检查锁。

## 两种检查的含义

| 检查方式 | 能提供什么 | 依赖 |
| --- | --- | --- |
| 本地规则检查 | 常见 Java 8 兼容性疑点、空 catch、控制台输出、TODO、同目录重复迁移版本、超过 500 行的 Service | Node.js |
| 完整质量体检 | 前述规则 + Java 8 构建与测试 + JaCoCo 覆盖率 + SonarQube Bugs / 漏洞 / Smells / 复杂度 / 重复率 / 安全热点 / 门禁 | Node.js、JDK 8、JDK 21、Maven（或项目 mvnw.cmd）、Docker 和 SonarQube |

本地规则是启发式提示，不代替编译或完整静态分析。它会屏蔽注释和字符串再匹配常见语法，但无法穷举全部 Java 9+ API，也无法判断自定义方法是否与新版 API 同名。源码行数包括注释及空行。未产生的指标显示“未检测”，从不生成模拟覆盖率。

1. 执行 `.\scripts\sonar-start.ps1`，或在平台“环境设置”点击启动。首次自动生成 `deploy/.env` 中的随机数据库密码。不要提交该文件。

SonarScanner 固定使用 `5.8.0.7211`，JaCoCo 固定使用 `0.8.14`。Token 通过环境变量传递，不写入命令行。平台输入的 Token 只在当前进程中保留，重启需重新填写，也可在启动前设置 `$env:SONAR_TOKEN`。

SonarQube 镜像默认是 `sonarqube:community`，数据库为 `postgres:17`。镜像首次拉取后，长期使用建议将 SonarQube 标签固定为已验证版本；升级前先备份数据库并核对官方升级路径。启动脚本不会自动修改系统内核参数，Docker / WSL 需满足 SonarQube Elasticsearch 要求。

## 业务项目的 JaCoCo 配置

将以下插件加入业务项目 `pom.xml` 的 `<build><plugins>`；多模块项目建议放在共同父 POM 的 `plugins` 中，让各模块执行。平台不会直接改写你的业务 POM。

```xml
<plugin>
  <groupId>org.jacoco</groupId>
  <artifactId>jacoco-maven-plugin</artifactId>
  <version>0.8.14</version>
  <executions>
    <execution>
      <id>prepare-agent</id>
      <goals><goal>prepare-agent</goal></goals>
    </execution>
    <execution>
      <id>report</id>
      <phase>verify</phase>
      <goals><goal>report</goal></goals>
    </execution>
  </executions>
</plugin>
```

如果 Surefire 配置了自定义 `argLine`，需要保留 JaCoCo 的参数，例如 `@{argLine} -Xmx512m`。测试不得禁用 fork，否则覆盖率代理无法生效。平台发现没有 `target/site/jacoco/jacoco.xml` 会明确失败。集成测试覆盖率需项目自行配置 JaCoCo integration / aggregate 报告；默认导入每模块标准单元测试 XML 报告。

也可以不用平台，直接运行：

```powershell
$env:JAVA8_HOME = 'C:\Program Files\Java\jdk8'
$env:JAVA21_HOME = 'C:\Program Files\Eclipse Adoptium\jdk-21'
$env:SONAR_TOKEN = 'your-local-token'
.\scripts\sonar-scan.ps1 -ProjectPath 'D:\projects\bidplatform_v2' -ProjectKey 'bidplatform-v2'
```

脚本退出时会恢复终端原来的 JAVA_HOME 和 PATH。

## 门禁与历史

- 本地规则门禁：启用规则中的高风险问题必须为 0。
- 平台完整体检门禁：**新增** Blocker / Critical 与安全漏洞为 0；新代码覆盖率默认 ≥60%，新代码重复率默认 ≤5%。没有新代码指标则显示“待评估”。
- 平台门禁与 SonarQube 服务器门禁分别显示。平台设置不会改动 SonarQube 的门禁配置。
- SonarQube 的 New Code 定义需在其项目设置中配置；平台“设为基线”仅影响平台的问题数量比较。
- 安全热点数量单独呈现，请在 SonarQube 审查，不将其假装为已确认漏洞。
- 门禁阈值和规则修改只影响后续扫描。历史保存当时的设置。
- 基线比较仅支持相同范围、方式与规则的整体扫描。本地问题按规则 / 文件 / 证据及出现次数匹配，SonarQube 问题按其唯一标识匹配，需结合源码确认。

## 数据、安全与维护

平台只监听 `127.0.0.1:4310`，SonarQube 只映射 `127.0.0.1:9000`，数据库不暴露主机端口。平台拒绝跨站请求和非本机 Host，读取源码限制在登记的项目目录内。本平台面向可信本机用户，登记的 Maven 项目必须可信，因为完整体检会执行项目构建过程。

`data/state.json` 保存项目、设置和历史摘要；`data/details` 保存每次报告的问题、执行日志与人工验收证据。迁移时先停止平台，再复制**整个数据目录**，不能只复制 state.json。路径不同时在“项目管理 / 编辑项目”更新项目名称和目录，保留项目 Key 及原有扫描记录。Token 不进入这些文件。构建日志来自项目自身，请避免业务测试输出其他敏感内容。

PostgreSQL 与 SonarQube 使用 Docker named volumes 保存分析历史。`.\scripts\sonar-stop.ps1` 只停止容器。**不要执行 `docker compose down -v` 或盲目清理 Docker 卷**。迁移 SonarQube 历史时需另做 PostgreSQL 备份与还原，单独复制本项目不会携带 Docker 数据。

后台一次执行一个扫描，避免互相清理构建产物。单个子进程 30 分钟超时，SonarQube 排队最多等待 10 分钟。超过 10,000 条 SonarQube 问题会报错而非静默截断。暂不提供多用户登录、分支/PR 分析、任务取消或自动修复。

# AI 生成代码质量控制（v1.2）

在侧栏打开 **AI 质量控制**，可以读取 GitHub.com 仓库最近 30 个开放 PR，选择 PR 后在本机检查 Java / SQL 改动。也可以直接填入仓库和 PR 编号。公开仓库无需 Token；私有仓库需要具有 Contents、Pull requests 读取权限的 GitHub Token。Token 仅保存在当前进程，也可通过 `GITHUB_TOKEN` 环境变量提供，不写入状态文件或分发包。

PR 检查记录固定的 HEAD / BASE 提交，源码内容校验 Git blob 哈希；如果检查期间 PR 更新则要求重试。每次最多 100 个改动文件、单文件 1 MB、源码合计 8 MB。差异缺失、截断、文件被排除或无可检查源码时，不会显示通过。源码仅用于临时本地检查，结束后清理；报告保留脱敏证据与提交信息。此版只读取 GitHub，不发布评论、提交状态或合并 PR。

新增三个可配置本地规则：硬编码凭据、外部命令执行、破坏性 SQL。启发式规则无法证明程序安全；请人工确认。凭据检查目前只覆盖 Java 中常见的字符串赋值，不能替代全面的秘密扫描。报告中的 Java / SQL 字符串证据会脱敏；主动打开本机源文件仍显示实际源代码。

每份完成的本地扫描或 PR 报告都可以记录五项人工验收：需求、边界与异常、测试证据、数据与权限、改动范围与恢复方案。勾选时需要至少 8 字证据。这是人工声明，不等于平台已执行测试。有高风险问题或检查不完整时，人工验收不能将报告标为已验收。后续代码修改必须重新扫描、重新验收。

PR 报告仅涉及改动行及删除附近上下文，不代表整个项目的质量；重复迁移检查仅能比较本次下载的文件，仍需完整项目扫描确认。此流程不执行 PR 内的构建脚本，不提供 SonarQube 原生多分支 / PR 分析，也不控制 GitHub 的合并权限。完整构建、测试与覆盖率请使用本机项目的完整体检。修复任务 Markdown 会同时导出范围、提交、限制与人工验收记录。

## 轻量运行与便捷部署（v1.3）

Windows 可双击根目录的 `start.cmd`，或在终端执行：

```powershell
.\scripts\start.ps1
# 自定义端口、独立数据目录和 JavaScript 堆上限
.\scripts\start.ps1 -Port 4320 -DataDirectory 'D:\CodeHealthData' -HeapLimitMB 256
# 检查已经启动的平台
.\scripts\check.ps1 -Port 4320
```

启动脚本会优先使用项目内的 `runtime/node.exe`，然后查找 PATH 中的 Node.js；也可以用 `-NodePath` 指定可执行文件。便携运行时应使用官方 Node.js 发行版；分发包不捆绑或下载运行时。脚本检查 Node.js 至少为 20。默认 JavaScript 堆上限为 256 MB；这是堆上限，不是平台总内存上限。直接 `node server.js` 启动则使用 Node 默认上限。Docker、JDK 和 Python 均不是本地规则检查的必需依赖。

环境设置增加“运行状态”，展示实际平台进程常驻内存、已用堆、运行时间和数据目录；这些数字不包含浏览器、Maven、JDK、SonarQube 或 PostgreSQL。`GET /api/health` 提供同样的本机健康信息。

历史详情按需从磁盘读取，不长期驻留进程内存。v1.4 起，首页刷新不读取问题详情，只接收最新计数、最近 25 次摘要、每个项目最多 12 个趋势点，以及必要的基线与最新整体报告摘要。历史日志、验收证据、GitHub 详情与基线对比在打开时读取。问题中心、扫描历史和验收记录通过服务端分页，每次默认只返回 25 条，最多 100 条。

升级旧数据时先保留 `data/state-before-details.json` 作为原始备份，然后逐份原子保存完整报告，再切换到摘要索引。没有删除旧历史、基线或人工验收。恢复旧版本前应停止平台并使用原始备份；新报告不在该升级备份中。数据目录只应由一个平台实例使用，测试或并行运行时请配置不同的数据目录。

已验证 60 份代表性报告的常驻索引序列化大小从 2,778,472 字节缩小到 15,971 字节（约 0.57%）；完整详情仍保存在磁盘上。这个数字不是进程总内存的降低比例。实际内存随项目、问题数和操作而变化，请以“运行状态”为准。

## 按需查询与稳定搜索（v1.4）

- 总览与环境页不读取最新问题详情。总览计数来自最近一次已完成的整体检查摘要，局部 Git / PR 检查仍然独立。
- 问题中心的搜索、风险筛选与项目筛选由后台执行；只读取相关项目的最新整体报告，一次只保留当前页与最后一页的匹配记录。完整导出使用相同的筛选规则，不局限于当前页。
- 扫描历史可按项目、执行状态和检查方式筛选。翻页可以访问全部历史，首页仅返回少量摘要不影响旧历史、基线或详情访问。
- 快速改变搜索或筛选会取消旧请求，并校验请求顺序。检查结果更新时会重新读取，避免旧响应覆盖新查询。
- 验收记录异步刷新只更新列表，不覆盖正在输入的 GitHub 仓库、Token 或 PR 编号。
- 问题 JSON 导出逐条写入临时文件，完成后原子替换；下载采用文件流，避免一次读入整份大报告。写入失败不会向用户返回成功文件。

本机接口：`GET /api/state` 为轻量总览；`GET /api/issues` 支持 `projectId`、`severity`、`search`、`offset`、`limit`；`GET /api/history` 支持 `kind=scan|quality`、`projectId`、`status`、`mode`、`offset`、`limit`。默认每页 25 条，limit 最大 100；越界页回到最后一页；非法筛选会明确报错。历史索引仍常驻后台内存，单份详情仍作为一个 JSON 文件读取，后续可进一步优化超大工作空间。

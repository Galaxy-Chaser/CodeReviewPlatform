# 代码实现质量验收流水线

适用于 CodeHealth v1.16。平台侧栏「验收流水线」是入口；项目管理和扫描详情也能打开。验收目标是：需求有明确条件，自动检查有真实报告，业务场景有实际结果，交付证据齐全，并且结论对应当前代码和当前方案。

## 一、八阶段流程和完成条件

### 平台自身迭代的自动检查

推荐点击「查看本轮验收」→「开始本轮验收」，连续完成下述平台自检和八项页面回归。只有完整证据对应同一版源码，本轮自动验收才通过；中断或失败不能使用以前的成功补齐。原有两个独立入口仍可用于定位问题。GitHub 提交也会运行同样验收，说明见 [自动验收使用说明](AUTOMATED-ACCEPTANCE.md)。

在同一页面点击「检查平台自身」→「开始平台自检」。平台固定使用当前 Node 检查 JavaScript 语法并执行所有 `test/*.test.js`，不接受外部命令或项目参数。只有测试完整执行、数量一致、没有失败/取消/跳过/待办、执行期间纳入核对的文件没有变化，才能显示「平台自动自检通过」。每次打开或点击「重新核对结果」都会核对当前文件；代码变化或无法核实时，旧成功结果不能证明新版本通过。

结果保存在平台数据目录，可下载实际测试输出与文件指纹，随数据备份恢复。页面默认显示最近一次结果，之前的自检报告仍保留在 reports 导出目录。也可使用 `npm run check:platform` 在终端执行同样检查，生成独立报告。自检超时为两分钟，输出有大小限制；未完成或汇总无法核实时失败。自动自检不替代人工业务/视觉验收，也不证明真实 JDK/Maven/Sonar 环境已通过。

版本核对 v2 新增页面与服务代码；v1 的旧指纹需重新扫描，历史记录不删除。outputs/dist/coverage 作为生成目录排除，不应放置需验收的手写源码。

| 阶段 | 执行方式 | 完成条件 | 未满足时怎么办 |
| --- | --- | --- | --- |
| 1. 需求与方案 | 人工定义，平台核对 | 方案已按业务调整并确认；若方案要求任务约定，扫描绑定的约定必须完整 | 补齐目标、范围、约束、验收条件，保存后重新检查 |
| 2. 环境与准备 | 自动 | 本次检查的目录、构建工具和服务准备条件已通过 | 从「检查运行环境」查看缺失项，修复后重跑 |
| 3. 本地风险 | 自动 | 规则检查完成，没有本地高风险 | 按问题位置修复后重跑；规则仅是启发式检查 |
| 4. 构建与自动测试 | 完整模式自动 | 本次构建成功，有可核实的新测试报告，执行数达到要求，没有失败或错误；禁止跳过时跳过数为零 | 修复构建或测试；旧报告和没有执行的测试不能充数 |
| 5. 综合质量门禁 | 自动 | 当次规则、项目要求和实测指标全部通过 | 修复风险或补齐真实分析数据；未知结果不能通过 |
| 6. 多场景验证 | 绑定测试自动采集；其余人工执行并登记 | 每个必测场景通过，可选场景通过或有明确不适用理由；没有失败、未验证或失效证据 | 按场景输入和步骤执行，登记实际差异与可复现证据 |
| 7. 交付证据 | 人工 | 需求、边界异常、测试、数据权限、范围回退五类确认均有至少 8 字的证据 | 在「填写交付验收证据」补齐实际记录 |
| 8. 版本核对 | 自动 | 报告是项目最新一次检查，方案版本仍为当前版本，纳入核对的源文件内容一致 | 代码或方案变化后按新版本重跑；重新核对不能替代测试 |

总状态为「检查正在执行」「验收受阻」「待完成场景与证据」或「本次验收条件已满足」。失败与未知条件不会因人工勾选被解除。最新一次检查失败时，也不能用之前的成功报告宣布当前版本通过。

## 二、使用步骤

1. 注册本地项目，填写项目的任务约定和质量要求。性能数字、权限规则、兼容版本、错误响应、允许改动范围和恢复目标必须按业务明确。
2. 在验收流水线选择项目，点击「建立验收方案」。平台提供 8 类、30 个场景模板，每个都有输入、验证步骤和预期结果。
3. 将泛用描述改成实际条件，例如“金额上限”改成“单笔金额不超过 10000.00；10000.01 应拒绝”。可新增或移除场景，每个方案保留 1–60 个场景，至少一个必测。
4. 根据范围选择自动要求。默认要求完整构建、自动测试和质量分析、完整任务约定、至少实际执行 1 个测试。可设置最低数量以及禁止跳过测试。模板需要明确确认后才能按方案执行。
5. 点击「检查运行环境」，处理缺失项，然后点击「按方案执行」。自动阶段会运行当前平台已有检查，不会执行场景文字中的任意命令。
6. 检查完成后，按各场景步骤在相应测试环境实际验证，再点「记录场景结果」。失败应登记差异，不要先填通过再寻找证据。
7. 修复导致失败的问题。代码改变后重新检查；新检查的场景结果从未验证开始，旧证据保留在旧报告。代码未改变、仅修订记录时，可以登记复验，历史记录仍可查看。
8. 填写五类交付证据，点击「重新核对流水线」。所有条件满足后再交付，导出详细验收记录作为证据。

「导出详细方案」适合分配验证任务；报告中的「导出详细验收记录」包含方案版本、阶段判断、具体步骤、当前证据、有限的修订历史和未满足条件。原有修复任务清单也会包含流水线内容。

## 三、30 个模板场景覆盖范围

| 类别 | 场景 | 重点检查 |
| --- | --- | --- |
| 正常功能 | 正常主流程；业务分支与状态转换；接口与错误约定 | 返回和持久化状态一致，非法状态不能转换，失败不会伪装成功 |
| 输入边界 | 空值与缺失；最小/最大与临界点；中文/Unicode；精度/时区/日期；超长输入与大集合 | 必填校验、越界、字符往返、金额舍入、时间含义及资源限制 |
| 异常与依赖故障 | 非法格式；超时与依赖不可用；部分失败；重试与取消 | 超时和重试有界，失败可诊断，不留下半完成状态 |
| 权限与安全 | 未登录/失效凭据；越权/租户隔离；注入/路径/命令参数；敏感信息与日志脱敏 | 服务端授权，外部输入不能扩大权限，输出不泄露测试凭据 |
| 数据与并发 | 重复提交；并发竞争；事务回滚；重启读取；历史数据迁移 | 不重复写入、丢失更新或半提交，恢复后状态可解释 |
| 性能与资源 | 响应时间/吞吐；内存/连接/资源泄漏 | 有明确负载和目标，记录响应分位数、错误率、稳定资源趋势 |
| 兼容与回归 | 目标运行版本；原有功能回归；接口联调；配置差异 | 目标环境能运行，相邻调用方不受破坏，错误配置明确报错 |
| 恢复与可观测性 | 回退演练；故障追踪；范围与交付核对 | 备份可恢复，故障能定位，交付和允许范围一致 |

每个模板场景的详细输入、步骤和预期可在页面展开查看或导出。模板中的“可说明不适用”不是自动跳过：没有记录理由仍然是未验证。账号权限、数据库、外部服务、负载、迁移和恢复相关场景应按项目实际情况改为必测。故障、压力、迁移和回退演练使用隔离环境与副本。

## 四、结果与证据规范

- **未验证**：尚未执行或撤回结论，不能计为通过。
- **通过**：实际结果符合预期；实际结果和验证证据均至少 8 字。平台核对的是证据记录与代码版本，不自动判断文字是否真实。
- **失败**：结果不符合预期，直接阻断。记录触发输入、期望和实际差异、可重现步骤。
- **不适用**：仅可用于非必测场景，两项文字分别说明原因和核对依据；必测场景不能用它跳过。
- **需重核**：证据保存时的代码不是扫描版本，或缺少可核对的版本信息；保留记录，但不能用于通过判断。

示例（并发场景，数值应改为真实项目条件）：

> 输入：测试账户余额 100.00，同时提交两个扣款 80.00 的请求。预期：最多一个成功，余额 20.00，另一请求明确拒绝。
>
> 实际结果：一个成功，一个余额不足，最终余额 20.00，只有一条成功流水。
>
> 验证证据：测试环境版本、执行时间、并发执行方式、脱敏请求编号、两次响应和数据库查询结果的保存位置。外部文件由项目自行保管，平台保存文字引用，不上传附件。

性能证据需包含硬件/配置、数据量、并发数、持续时间、响应分位数和错误率；兼容证据需包含运行版本和实际构建/启动结果；恢复证据需包含备份版本、步骤、耗时和恢复后的关键核对。不要把密码、Token 或真实个人数据写入证据。

## 五、本地与完整验收的区别

本地方案只运行本地规则，不构建项目，不执行自动测试，不测覆盖率。关闭完整要求后，最低自动测试数为 0，禁止跳过选项关闭；阶段会明确显示「方案未要求」。这种方案满足时，只能说明其声明范围的条件满足。

完整方案使用平台原有的 JDK 8 构建、JDK 21 分析、Maven 和 SonarQube 流程，环境配置见 README。自动统计只接受本次构建后更新的 Surefire/Failsafe 报告。测试数量并不证明这 30 个业务场景已覆盖，场景仍需实际验证和登记。项目质量要求独立生效，关闭流水线某项要求不会降低已保存的项目要求。

当前开发环境尚未实跑完整 JDK/Maven/Sonar 流程。本轮验证了报告解析、判断逻辑、本地真实扫描和缺依赖时明确失败的行为；不把代表性报告测试当成真实 Java 构建成功。

## 六、版本、并发与保留

每次保存方案生成新版本；每次扫描保留当时方案全文。修改方案不改写历史，但旧版本不能作为当前方案验收。新扫描不会自动继承场景“通过”。记录证据时自动核对源码，代码改动会阻断旧报告；文件内容恢复也不会把曾在不一致版本下录入的证据变成有效证据。

保存时会检查页面加载的版本，其他窗口已保存的修改不会被旧表单覆盖。检查进行中不能同时修改方案或结果。场景保留当前记录以及最多 19 条之前的修订记录；不等于无限审计历史。

当前方案、报告中的冻结方案、结果和导出进入原有数据备份/恢复流程。备份不包含业务源码、运行凭据、外部证据文件或 Sonar 数据库。源码核对只覆盖原有报告约定的文件范围，不能检测数据库、部署配置及外部依赖变化，这些仍需相应场景验证。

## 七、自动测试绑定与页面回归（v1.15）

编辑方案，在场景的“绑定自动测试（可选）”中填写实际报告里的 `测试类#测试名称`，例如 `demo.FlowTest#normal`。测试名称必须与 Surefire/Failsafe XML 的 classname 和 name 完全一致；参数化测试需要使用报告中的实际名称。绑定场景必须要求完整体检，保存后重新执行整个项目的完整检查。平台沿用原有 Maven 构建，不单独执行任意绑定字符串。

只有本次构建开始后更新、结构与汇总一致的测试报告可作为证据。精确匹配且构建成功才能记录通过；任意匹配失败记录失败；没有匹配、跳过、仅本地检查或无法核实均保持待验证。绑定场景禁止人工覆盖、豁免或改成通过，需要修复后重跑。测试报告只能证明具体测试的实际结果，不能证明测试断言充分或业务需求全覆盖。

平台自身页面回归与项目完整体检是两个入口。在“验收流水线”点击“查看页面回归”查看或启动八项固定浏览器流程。它使用独立示例数据，不读取生产项目，保存截图和报告并核对当前平台代码。安装和结果解释见 [自动验收使用说明](AUTOMATED-ACCEPTANCE.md)。
